Deployment templates for Dynatrace Google Cloud Extension
=========================================================

## Overview

These Terraform scripts provision all GCP resources and configure the Dynatrace side of the integration
in a single `terraform apply`. The scripts create a service account, enable required APIs, grant necessary
permissions, and automatically enable GCP monitoring in Dynatrace — no separate `dtctl` or UI step is required.

## Important: Your Responsibility

The following artifacts are **not stored or regenerated by Dynatrace**. You are responsible for preserving them:

- Your `terraform.tfstate` (and any backups)
- The variable files you provide for your deployment (`config.auto.tfvars`, `terraform.tfvars`)

If these are lost, you will need to re-run onboarding from scratch or recreate them manually using the provided example files (`config.auto.tfvars.example`, `terraform.tfvars.example`).

## How to Use the Scripts

1. **Prepare the Variables** — copy the example files and fill in the values for your environment:
   ```bash
   cd template
   cp config.auto.tfvars.example config.auto.tfvars
   cp terraform.tfvars.example terraform.tfvars
   ```
   Edit `config.auto.tfvars` with your Dynatrace connection settings and `terraform.tfvars` with your
   deployment configuration (region, monitoring scopes, etc.). If you are using the Dynatrace UI or
   `dtctl` to onboard, `config.auto.tfvars` will be pre-filled for you.

2. **Run the Scripts**:
   - Initialize the Terraform scripts:
     ```bash
     terraform init
     ```
   - Check the planned changes:
     ```bash
     terraform plan
     ```
   - Apply the changes to create the resources:
     ```bash
     terraform apply
     ```

3. **Cleanup Resources (Optional)**:
   - To remove all created resources, run:
     ```bash
     terraform destroy
     ```

## Complete Onboarding

GCP monitoring is enabled automatically by `terraform apply` — no separate `dtctl enable` step is
needed. Terraform supports two onboarding flows:

- **IaC-flow** (default, `mconfig_id` omitted or empty): Terraform creates a new monitoring
  configuration (mconfig) using the payload in `mconfig_value`. No UI or `dtctl` step is needed to
  pre-create the mconfig. Edit `mconfig_value` in your `terraform.tfvars` to configure feature sets,
  filtering, enrichment, and other settings before running `terraform apply`.
- **App-flow** (`mconfig_id` provided): Terraform imports and enables the existing mconfig
  pre-created by the Dynatrace UI or `dtctl`. This is how UI/dtctl users work.

Before running `terraform apply`, export your Dynatrace API token so Terraform can enable the
monitoring configuration:

```bash
export TF_VAR_dynatrace_settings_token="<your Dynatrace settings token>"
```

The token requires the following scopes:
`settings.read`, `settings.write`, `extensions:configurations:read`, `extensions:configurations:write`

Note: the terraform runner account itself should have following roles:

```text
roles/iam.serviceAccountAdmin
roles/iam.serviceAccountUser
roles/serviceusage.serviceUsageAdmin
roles/storage.objectUser
roles/resourcemanager.projectIamAdmin
roles/resourcemanager.folderIamAdmin
roles/resourcemanager.organizationIamAdmin
roles/pubsub.admin
roles/cloudasset.owner
roles/dataflow.admin
roles/logging.admin
```

`roles/iam.serviceAccountUser` is required for the asset feed push subscription, which
configures an OIDC token for the customer SA (`create-asset-feed.tf`) — creating it requires
`iam.serviceAccounts.actAs` on that SA, which `roles/iam.serviceAccountAdmin` alone does not grant.

`roles/dataflow.admin` and `roles/logging.admin` are required only when `logs_enabled = true`.

### Configuration files

Two variable files (inside the `template/` directory) control your deployment:

- **`template/config.auto.tfvars`** — the identity/connection block (`project_id`, service account,
  `tenant_id`, `mconfig_id`, `tenant_url`), pre-filled by the Dynatrace UI. You normally don't edit
  this. `mconfig_id` is optional: omit it (or leave it empty) for IaC-flow, or provide it for
  App-flow (see *Complete Onboarding* above).
- **`template/terraform.tfvars`** — your deployment settings: `region`, `logs_enabled`,
  `asset_feed_enabled`, the monitoring scopes (`project_ids_for_monitoring` /
  `folder_ids_for_monitoring` / `organization_ids_for_monitoring`), the asset-feed scopes
  (`project_ids_for_asset_feed` / `folder_ids_for_asset_feed` / `organization_ids_for_asset_feed`),
  `custom_labels`, and `mconfig_value` (IaC-flow only — the full monitoring configuration payload
  as JSON; edit feature sets, filtering, enrichment, and other settings here). Edit this file.

Set `asset_feed_enabled = true` to turn on the asset feed. When enabled, each asset-feed scope
defaults to inheriting the matching monitoring scope (the asset feed follows what you monitor); set
a list to target different scopes, or `[]` to disable that scope type.

If the same variable is set in both, `config.auto.tfvars` wins. The `dynatrace_api_token` is never
stored in either file — supply it via `TF_VAR_dynatrace_api_token` when `logs_enabled = true`.

## Log Forwarder Pipeline (optional)

Set `logs_enabled = true` in `terraform.tfvars` to enable the optional log forwarder. When enabled,
Terraform provisions a streaming pipeline that exports Cloud Logging entries to the Dynatrace Log
Ingest API:

```
Cloud Logging sink → Pub/Sub → Dataflow streaming job → Dynatrace Log Ingest API
```

Failed messages are routed to a dead-letter Pub/Sub topic and subscription for inspection or replay.

**Prerequisites before applying with `logs_enabled = true`:**

- Ensure `gcloud` is authenticated; the runner account needs `roles/dataflow.admin`,
  `roles/logging.admin`, and `roles/secretmanager.secretAccessor`
- Export a Dynatrace API token with the `data-acquisition:logs:ingest` scope as an environment variable:
  ```
  export TF_VAR_dynatrace_api_token="xxx"
  ```

> **Note:** The worker image is public and is pulled directly from Docker Hub by Dataflow at job
> launch — no local `docker`/`gcloud` image steps are required. This assumes the Dataflow workers
> have outbound access to Docker Hub (the default).

## Permissions granted

The service account is granted the following roles based on the monitoring scope you configure:

| Role | Grants | Applied at |
| ---- | ------ | ---------- |
| `roles/monitoring.viewer` | Fetch time-series data and metric descriptors | project, folder, org |
| `roles/cloudasset.viewer` | Fetch resource inventory via Cloud Asset Inventory | project, folder, org |
| `roles/compute.viewer` | Fetch compute regions and zones | project, folder, org |
| `roles/browser` | List and get resources within the binding scope: projects only at project scope, folders and projects at folder scope, the organization and all folders and projects at org scope | project, folder, org |

> **Note:** `roles/browser` is bound at the configured scope, so the resources it can list depend
> on where the binding is applied. Configuring `project_ids_for_monitoring` alone limits browser
> to listing those projects only — folder listing is not available at project scope. Use
> `folder_ids_for_monitoring` or `organization_ids_for_monitoring` to enable folder listing.
> Enumerating the projects within `project_ids_for_monitoring` only and using folder filtering in
> the Dynatrace monitoring configuration will not work, as Dynatrace needs to discover the folder/project hierarchy.
